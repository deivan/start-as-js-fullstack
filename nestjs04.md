## Тема: Робота з декоратором Module

### Структура та призначення декоратора @Module

У NestJS модулі (`@Module`) є основним механізмом інкапсуляції та організації коду. Кожен додаток має щонайменше один кореневий модуль (`AppModule`), який є точкою старту для побудови графа залежностей, і зазвичай безліч функціональних модулів (наприклад, `UsersModule`, `ProductsModule`).

Декоратор `@Module()` приймає об'єкт конфігурації з чотирма основними масивами:

1.  **`controllers`**: Масив контролерів, які мають бути ініціалізовані в межах цього модуля. Вони відповідають за обробку маршрутів та HTTP-запитів.
2.  **`providers`**: Масив провайдерів (найчастіше це Сервіси, Репозиторії, Стратегії тощо), які ініціалізуються інжектором залежностей NestJS і містять основну бізнес-логіку. За замовчуванням вони доступні лише всередині цього модуля.
3.  **`exports`**: Масив провайдерів (сервісів), які цей модуль "віддає" назовні. Якщо інший модуль імпортує поточний модуль, він отримає доступ лише до тих сервісів, які вказані в масиві `exports`.
4.  **`imports`**: Масив інших модулів, які експортують провайдери, необхідні для роботи поточного модуля.

### Інкапсуляція та обмін даними між модулями

За замовчуванням усі провайдери всередині модуля жорстко інкапсульовані. Це означає, що вибудувана безпечна архітектура: `ProductsService` з одного модуля не може бути випадково або прямо використаний в `UsersController` іншого модуля.

Щоб правильно поділитися сервісом між різними сутностями, необхідно виконати два кроки:

1.  Експортувати потрібний сервіс з його рідного модуля через масив `exports`.
2.  Імпортувати цей модуль туди, де він потрібен (додати до масиву `imports` цільового модуля).

Приклад базового експорту:

```ts
import { Module } from '@nestjs/common';
import { ProductsController } from './products.controller';
import { ProductsService } from './products.service';

@Module({
  controllers: [ProductsController],
  providers: [ProductsService],
  exports: [ProductsService], // Відкриваємо ProductsService для інших модулів
})
export class ProductsModule {}
```

### Глобальні модулі (Особливість декоратора @Global)

У реальних проектах часто існують сервіси, які потрібні практично всюди. Наприклад: модуль підключення до бази даних, сервіс конфігурації (для роботи зі змінними оточення `.env`), глобальний логер або модуль інтеграції зі стороннім сховищем (наприклад, Redis або AWS S3).

Імпортувати такі загальновживані модулі в масив `imports` кожного нового функціонального модуля вкрай незручно. Це призводить до розростання бойлерплейт-коду та дублювання імпортів. Саме для вирішення цієї архітектурної проблеми використовується декоратор `@Global()`.

**Як працює глобальний модуль:**
*   Декоратор `@Global()` ставиться безпосередньо над декоратором `@Module()`.
*   Коли модуль позначається як глобальний, його достатньо імпортувати **лише один раз** за весь життєвий цикл додатку (найкраще це робити в кореневому `AppModule`).
*   Після цього єдиного імпорту, всі провайдери, які цей модуль розшарює через масив `exports`, стають магічним чином доступними абсолютно всьому додатку. Вам більше не потрібно прописувати цей модуль в масиві `imports` інших модулів — ви можете просто інжектувати глобальні сервіси прямо в конструктори контролерів чи інших сервісів.

Приклад створення глобального модуля конфігурації:

```ts
import { Module, Global } from '@nestjs/common';
import { CustomConfigService } from './custom-config.service';

@Global() // Робимо модуль глобальним
@Module({
  providers: [CustomConfigService],
  exports: [CustomConfigService], // Експортуємо сервіс для глобального доступу
})
export class CustomConfigModule {}
```

**Архітектурне застереження:**
Попри зручність `@Global()`, розробники NestJS наполегливо радять не зловживати цим інструментом. Використовувати його слід обережно і виключно для тих модулів, які дійсно мають загальносистемне призначення. 

Робити всі підряд функціональні модулі (наприклад, модуль користувачів або замовлень) глобальними — це антипатерн. Це руйнує саму ідею модульної архітектури, ускладнює відстеження залежностей і перетворює код на "монолітну кашу", де втрачається контроль над тим, яка частина коду від чого залежить.
